# ChatGPT Voyager 理工用户产品与开发路线

## 路线状态

- 基准日期：2026-07-19
- 产品阶段：已有 `v0.3.0` 基线，当前工作区包含尚未提交的长对话索引和问题清单导出增强
- 目标用户：经常处理数学、科研或工程类长对话的理工类用户
- 核心策略：先验证“长技术对话整理与公式复用”是否能形成重复使用，再扩展组织、搜索和商业化能力
- 开发原则：每个阶段必须通过行为验收和用户验证门槛，未通过时不得用新增功能掩盖核心问题

## 商业假设

核心假设：

> 经常处理数学、科研或工程类长对话的用户，会因为“完整索引、可靠导出、公式可直接进入 Word/WPS/Markdown”而主动安装并持续使用 Voyager。

这个假设包含四个必须分别验证的子假设：

1. 用户确实会在单个 ChatGPT 会话中积累难以回看的长技术对话。
2. 用户需要把其中一部分问题、回答、代码、表格和公式复用到论文、报告、作业或技术文档。
3. 现有复制粘贴和通用导出工具会造成明显的查找、格式修复或公式重录成本。
4. Voyager 能把这项任务的时间和错误率降到足以促成重复使用的程度。

若真实用户只偶尔导出普通文本，或仍愿意用复制粘贴解决问题，则该假设不成立；此时应停止扩展功能，将项目转为维护型开源工具或重新定位。

## 目标用户和使用场景

### 首要 ICP

- 数学、物理、计算机、电子、机械、控制、统计等专业的研究生和高年级本科生。
- 经常让 ChatGPT 推导公式、解释论文、调试算法、整理实验结果，并将内容写入 Word、WPS、Markdown 或 LaTeX 文档。
- 每周至少出现一次 20 轮以上的技术对话，且曾经手工查找旧问题、修复公式或分段复制内容。

### 次要 ICP

- 需要整理课程材料、解题过程或讲义的理工科教师。
- 使用 ChatGPT 生成技术方案、算法说明、故障分析和内部文档的工程师。

### 暂不服务

- 主要使用短对话、图片生成或日常闲聊的普通用户。
- 只需要提示词模板、聊天皮肤或通用文件夹管理的用户。
- 在尚未验证 ChatGPT 核心闭环前，要求 Claude、Gemini 等多平台统一管理的用户。

## 核心工作流

```mermaid
flowchart LR
    Chat["产生长技术对话"] --> Find["通过目录和搜索定位问题"]
    Find --> Select["选择需要复用的问答"]
    Select --> Inspect["确认回答、代码、表格和公式完整性"]
    Inspect --> Export["导出到 Word / WPS / Markdown / PDF"]
    Export --> Reuse["进入论文、报告、作业或技术文档"]
    Reuse --> Return["下次技术对话继续使用 Voyager"]
```

Voyager 的核心价值不是“拥有很多 ChatGPT 增强功能”，而是让上述工作流更快、更可靠。不能改善该工作流的功能，不进入当前阶段。

## 产品指标

### 北极星指标

每周成功完成技术内容复用的用户数。一次成功复用至少满足以下一项：

- 导出包含技术内容的 Markdown、PDF 或后续 Word 文档；
- 将公式以 Word UnicodeMath 或 WPS LaTeX 成功粘贴到目标应用；
- 从 20 轮以上长对话中定位并复用历史问答。

### 首轮验证指标

| 指标 | 目标 |
| --- | ---: |
| 定向邀请并完成安装 | 至少 10 人 |
| 首次安装后完成一次核心任务 | 至少 7 人 |
| 7 天内重复使用至少 2 次 | 至少 5 人 |
| 明确表示停用后会影响现有工作流 | 至少 3 人 |
| 主动推荐、赞助或愿意付费 | 至少 2 人 |
| 典型技术对话的核心任务成功率 | 至少 80% |

这里统计真实行为，不以“觉得不错”“以后可能会用”等口头反馈代替。

## 功能优先级

### 必须做好

- 长对话问题识别、缓存恢复、搜索和可靠定位。
- 选择问题及对应回答，明确提示未加载或不完整内容。
- 保留标题、列表、代码块、表格和公式的技术内容导出。
- Word UnicodeMath、WPS LaTeX、Markdown LaTeX 的可验证公式复制。
- 默认本地处理、最小权限和清晰的隐私说明。
- 针对 ChatGPT DOM 变化和历史问题的自动回归检查。

### 验证后再做

- 原生 `.docx` 或更稳定的 Word-ready 富文本导出。
- 跨对话搜索、收藏、标签和“研究项目”集合。
- 公式批量导出和公式兼容性诊断。
- Obsidian、Notion、Zotero 等技术工作流集成。
- 可选的语义总结和主题分段。

### 当前冻结或缩减

- 通用提示词库：不继续扩展，除非能直接服务技术内容复用。
- 通用文件夹：不继续做聊天侧边栏替代品；未来只考虑重构为“研究项目/技术资料集合”。
- 无实际效果的设置：在核心闭环稳定后实现或移除。
- 多站点适配、云同步、团队协作和付费系统：在重复使用得到验证前不开发。
- 第二套右侧问题横线：永久不恢复，继续与 ChatGPT 官方导航共存。

## 分阶段开发路线

### 阶段 0：锁定并发布稳定基线

- 建议版本：`v0.3.1`
- 预计周期：1 周
- 目标：把当前未提交实现整理成可加载、可验证、可交给首批用户的稳定版本。

开发范围：

1. 完成当前官方导航条目同步、问题模式 PDF/PNG 导出等在研改动的真实页面验收。
2. 执行短对话、长对话、重复问题、虚拟滚动、刷新恢复和未保存会话测试。
3. 在 Word 和 WPS 中验证代表性的分数、根号、求和、矩阵、上下标和文本函数公式。
4. 构建并从 `dist/` 重新加载验证，更新版本说明和已知限制。

退出门槛：

- `npm run check`、`npm run build` 和 `git diff --check` 通过。
- `docs/MANUAL_TEST_CHECKLIST.md` 中 P0 用例通过。
- 至少 20 个代表性公式在目标应用中记录通过或明确的兼容限制。
- 没有目录缺项、错误合并、错误定位、官方导航冲突或虚假完整导出等 P0 问题。

若未通过，只修复阻塞问题，不进入阶段 1。

### 阶段 1：两周技术工作流验证版

- 建议版本：`v0.4.0-beta`
- 预计周期：2 周
- 目标：用最小产品验证用户是否愿意重复使用核心闭环。

只保留五个用户可感知入口：

1. 打开技术对话目录并搜索问题。
2. 查看问题与回答的加载/完整状态。
3. 选择一个或多个问答进行导出。
4. 复制 Word、WPS 或 Markdown 公式。
5. 反馈一次成功、失败和需要人工修复的任务。

开发内容：

- 为首次使用提供不超过三步的引导，直接指向目录、选择问答和公式复制。
- 在导出前显示内容完整性提示：问题数、已加载回答数、公式数和缺失项。
- 建立本地、可主动导出的诊断记录，不默认上传对话正文或使用行为。
- 准备数学推导、论文解释、算法调试和工程分析四类验收样例。

用户验证：

- 手工邀请 10 名首批用户，不投广告、不做批量推广。
- 每人使用自己的真实长对话完成一次内容复用任务。
- 记录任务开始和结束时间、导出是否成功、公式修复次数、是否在 7 天内再次使用。

退出门槛：

- 至少 10 人安装、7 人完成核心任务、5 人在 7 天内重复使用。
- 至少 3 人表示停用后会影响工作流。
- 典型任务成功率达到 80%，严重公式损坏或内容缺失不超过 10%。

未达到门槛时，不做原生 Word、跨会话搜索或多平台适配；先判断是可靠性问题、使用频率不足还是目标用户选错。

### 阶段 2：可靠技术导出

- 建议版本：`v0.5.0`
- 预计周期：2 至 3 周
- 前置条件：阶段 1 的重复使用门槛通过
- 目标：让用户把内容真正交付到论文、报告和技术文档，而不只是下载一份聊天记录。

候选功能按用户证据排序：

1. 问题与回答成组选择，保留原始顺序和来源信息。
2. 导出预览，明确显示标题、段落、表格、代码块和公式转换结果。
3. 原生 `.docx` 或 Word-ready 富文本导出；仅在真实 Word 用户数量足够时实施。
4. 公式兼容性报告：标记已可靠转换、已回退为文本和需要人工处理的公式。
5. 为技术 Markdown 保留语言标记、表格和 LaTeX 边界。

技术工作：

- 在行为基线和浏览器测试建立后，按 DOM 适配、索引、定位、UI、导出拆分 `content.js`。
- 为技术内容建立统一中间模型，避免 Markdown、PDF、PNG、Word 各自重新解析页面 DOM。
- 增加包含公式、表格、代码、流式回答和虚拟滚动的浏览器级夹具。

退出门槛：

- 10 份真实技术对话中至少 8 份无需重新复制整段内容。
- 常见公式进入 Word/WPS 后，平均每 10 个公式人工修复不超过 1 个。
- 长对话导出不会把未加载回答声称为完整内容。
- 所有既有导航、缓存、目录和官方导航共存回归继续通过。

### 阶段 3：研究项目与跨对话复用

- 建议版本：`v0.6.0`
- 预计周期：3 至 4 周
- 前置条件：至少 20 名周活跃用户，且有明确的跨对话整理证据
- 目标：把一次性导出升级为可重复积累的个人技术资料工作流。

候选功能：

- 将选中的问答保存为“技术条目”，而不是只保存会话 URL。
- 按论文、课程、实验或工程项目建立本地集合。
- 跨会话搜索问题、回答、公式和代码片段。
- 记录来源 URL、会话标题、保存时间和用户标签。
- 支持 Markdown/JSON 备份和恢复，默认仍为本地存储。

退出门槛：

- 至少 30% 的周活跃用户在两周内重复使用项目集合或跨对话搜索。
- 用户保存的不只是链接，而是真正再次打开或导出的技术条目。
- 数据模型支持备份和恢复，不因 ChatGPT DOM 变化丢失已保存内容。

若用户主要只使用单次导出，则保留轻量导出工具定位，不建设复杂知识库。

### 阶段 4：发布、增长与有限商业化

- 建议版本：`v1.0.0`
- 前置条件：连续 4 周有稳定重复使用，且核心留存不是由开发者本人贡献
- 目标：建立可持续发布、反馈和维护机制。

范围：

- Chrome Web Store 正式页面、清晰的理工用户场景截图和隐私说明。
- 新版本迁移、兼容性说明、崩溃/诊断信息主动导出和反馈闭环。
- 根据用户行为决定是否提供付费能力。

可能的商业边界：

- 免费：长对话导航、搜索、Markdown 导出、单公式复制。
- 付费候选：批量 Word 技术导出、公式兼容性诊断、跨对话研究项目和高级集成。

不应把基础可靠性、数据取回或隐私保护设为付费功能。没有明确付费意愿前，不开发账户和订阅系统。

## 首批 10 名用户计划

1. 从身边高校实验室、研究生群、理工课程群和工程师同事中，定向寻找有真实长技术对话的人；优先选择已经手工修公式或整理聊天记录的人。
2. 由开发者一对一协助安装，让用户现场完成最近一次真实任务；观察其实际操作，不先讲解所有功能。
3. 七天后只追踪行为：是否再次使用、完成了什么文档、修了多少公式、是否愿意推荐；不把赞美当作留存。

首次沟通重点不是推销，而是确认过去行为：上一次从 ChatGPT 整理技术内容是什么时候、用了什么方法、花了多久、哪里出错。

## 阶段决策规则

每个阶段结束时只允许四种决策：

- `继续`：指标通过，进入下一阶段。
- `修复`：需求成立但可靠性不足，只修核心闭环。
- `收缩`：只有一部分用户或场景成立，进一步缩小 ICP 和功能范围。
- `停止/转维护`：没有重复使用或用户不愿改变现有行为，不再扩功能。

以下情况应立即停止功能扩张：

- 连续访谈 10 名目标用户，没有 3 人能说出最近一次真实痛点。
- 10 名安装用户中少于 3 人在 7 天内再次使用。
- 用户只使用通用导出，不使用目录、技术格式或公式能力。
- 为适配 ChatGPT DOM 投入的维护成本持续高于用户获得的实际价值。

## 开发执行顺序

1. 完成阶段 0：稳定并发布当前基线。
2. 完成阶段 1：两周真实用户验证，不增加非核心功能。
3. 根据阶段 1 数据决定是否进入可靠技术导出。
4. 只有出现跨对话重复整理行为，才建设研究项目和搜索。
5. 只有形成稳定留存和明确付费意愿，才建设商业化与多平台能力。

每个功能修复继续遵守 `AGENTS.md` 和 `REGRESSION_LOG.md`：修改前检查本地工作区和历史修复，修改后补充测试、记录回归并运行项目检查。
